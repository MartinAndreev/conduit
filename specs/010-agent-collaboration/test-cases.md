# 010 — Приемателни сценарии

Статус: **спецификация на бъдеща проверка; тестове не са реализирани или
изпълнявани**. Следват [spec.md](spec.md) и
[review-findings.md](review-findings.md). Нито един сценарий не разрешава
live inference, инсталация, мрежова операция или промяна в реален проект.

## Етап 1 — Council

| ID | Сценарий | Очаквано проверимо поведение |
| --- | --- | --- |
| C01 | Въпрос, две роли, назначения и разрешен контекст | Подготовката показва точните участници, ограничения и бюджет; snapshot е записан преди dispatch |
| C02 | Липсващ model/harness или неподдържана задължителна capability | Конкретна причина преди launch; няма друг платен модел или по-широки права |
| C03 | Двама участници дават първи позиции | Никой не получава чуждата позиция преди reveal, включително през workspace/inbox/native session history |
| C04 | Промяна на оригинален source след създаване на snapshot | И двамата получават фиксираните одобрени байтове; друга версия не влиза тихо в кръга |
| C05 | Източник, разрешен само за A, съдържа уникален маркер | При общ reveal източникът е изключен от входа на този Council; маркерът не достига B или синтезатора |
| C06 | Опити за project write, временно write-then-restore, symlink escape или четене на чужда позиция | Ограничението спира ефекта/достъпа; само post-hoc clean diff не покрива сценария |
| C07 | Ambient hook/MCP tool се опитва да промени проект или да прочете credential/изпрати данни | Неодобреният инструмент/ефект е недостъпен; няма credential в запис, контекст или диагностика |
| C08 | Native candidate идва преди StartTurn да върне binding, после success terminal | Предварително активният consumer го задържа ограничено; след проверка се записва точно един принос за правилния turn |
| C09 | Същият ранен candidate, последван от failed/cancelled terminal | Няма приет принос; наличният материал е отделно означен като частичен |
| C10 | Candidate с чужд assignment, round, participant или context revision | Не се приписва на текущата задача; няма приемане или обновяване на readiness |
| C11 | Дублирано събитие или два различни payload-а за един принос | Идентичният дубликат е no-op; конфликтът е видим, без last-write-wins |
| C12 | JSON accept в commentary, unknown phase, truncation или event gap | Нула формални ACK-и; текстът/пропускът е видим; няма измислена завършеност или сплайсване през gap |
| C13 | Две уверени позиции срещу едно конкретно възражение | Възражението остава отделно видимо и отворено независимо от мнозинството и синтеза |
| C14 | Синтезатор пропуска възражение или цитира несъществуващ evidence | Оригиналното възражение остава отворено; forged reference не го разрешава |
| C15 | Отговор предлага resolution или човек приема риска | Моделното предложение само не затваря въпроса; валидно основание/човешко решение се записва с произход |
| C16 | Липсващ участник или изчерпан round/time/context budget | Bounded partial/no-decision резултат с липсващите части; няма мълчаливо намален състав, съгласие от мълчание или безкраен нов кръг |
| C17 | A → B → A при лимит един жив процес | Няма припокриване на притежавани процеси; следващият launch следва потвърденото освобождаване, контекстът е възстановен от разрешени записи |
| C18 | Turn приключва, но Close/cleanup timeout оставя неизвестно освобождаване | Caller връща bounded partial outcome; слотът остава зает, B не стартира; cleanup owner и eventual result са наблюдаеми |
| C19 | Двама dispatcher-а обработват един command ID | Един атомарен claim и едно harness извикване; различен payload със същия ID е конфликт |
| C20 | Срив след claim/dispatch преди запис на outcome | Записът остава interrupted/unknown; рестарт или lease timeout не предизвиква втори dispatch; нов опит спазва recovery gate |
| C21 | Persistence отказва преди/след външния ефект | Преди durable claim няма dispatch; след ефект не се обявява безопасен retry или пълен rollback; известните части се разграничават |
| C22 | Cancellation при текущ I/O, после нов планиран ход | Нов ефект не започва след установена cancellation; текущият remote ефект/cleanup не се обявява автоматично за отменен |
| C23 | Съобщение за следващ кръг или неизвестен steer receipt | Репликата не прави автоматичен Steer/+1; неизвестната корекция не се release-ва/преизпраща автоматично |
| C24 | Engram е изключен | Council, историята и човешкият избор работят; няма стартиран Engram, индекс или memory activation |
| C25 | Валиден финален Council и човешки избор | Отчетът е консултативен; нула code writer, spec approval, commit или merge като страничен ефект |
| C26 | Прекъсване и повторно отваряне на отчета | Запазени приноси, възражения, версии, missing/unknown статус и отделен cleanup outcome; не се симулира native resume |
| C27 | Прекалено голям payload, неразрешен artifact ref или чужд sender/project | Ограничен отказ преди persistence/reveal; няма cross-project достъп или impersonation |
| C28 | Намаляване на контекста за следващ ход | Задължителният snapshot и отворените възражения се пазят; при невместимост ходът не започва с тихо отрязани задължителни данни |

## Етап 2 — Договаряне

| ID | Сценарий | Очаквано проверимо поведение |
| --- | --- | --- |
| N01 | Backend предлага schema, frontend иска промяна, всички отговарят на v2 | Agreement записът сочи точните v2 байтове/hash, контекст и required participants |
| N02 | Промяна на nullability, error schema или artifact след ACK за v1 | ACK за v1 не дава готовност за v2; старото решение остава исторически проследимо |
| N03 | Нормален нов turn/native session на същия логически участник | Валидното записано приемане се пази; native session ID не е identity на участника |
| N04 | Смяна на участник, промяна на required membership или late output от стар опит | Новият състав изисква приложими отговори; старият опит не може да приеме от името на новия |
| N05 | Proposer премахва несъгласен участник, някой мълчи или пише accept в commentary | Няма промяна на required membership/готовността без упълномощено действие; няма implied ACK |
| N06 | Concurrent accept/withdraw/change преди финалния преход | Expected revision/membership проверката сериализира решението; остаряло приемане не отключва план |
| N07 | Collaboration freeze за v1, но планът вече е v2 | Собственикът на плана отказва стария dispatch; fake writer отчита нула calls |
| N08 | След разрешението mutable path вече съдържа друг договор | Launcher използва одобрения immutable input или отказва mismatch; никога v2 под одобрение за v1 |
| N09 | Две конкурентни заявки за разрешения launch | Един claim от execution owner; agreement record сам не е launch authority |
| N10 | След започнал run пристига предложение за нов договор | Старият run пази своя snapshot; създава се successor/change request без тиха mutation или твърдение за спрени writers |
| N11 | Две договарящи роли при един процесен слот, timeout или взаимно чакане | Кратки приключващи ходове; няма polling worker, заел ресурса на другия; спорът приключва bounded и видимо |
| N12 | Routine clarification в дадения scope срещу архитектурна промяна | Първото не иска approval за всяка реплика; второто не получава автоматично право от агентско съгласие |
| N13 | Агентите са съгласни, но бъдещата имплементация нарушава schema | ACK не заменя contract verification; независимата execution проверка отчита несъответствието |

## Квалификация и оценка

| ID | Сценарий | Доказателство за приемане |
| --- | --- | --- |
| Q01 | Детерминистични fake adapters за success/failure/race пътищата | Изпълнени приложими C/N сценарии с наблюдавани effect counts, bounds и cleanup; без реални credentials/project writes |
| Q02 | Два различни реални harness-а участват в Council | Точни executable/version/model/mode, разрешен snapshot, реална размяна на позиции/възражения, доказана изолация и contribution channel; отделно записани неизвестни capabilities |
| Q03 | Един harness е unsupported или е заменен с fake | Cross-harness gate остава непокрит; нито fixture, нито executable detection се отчита като live успех |
| Q04 | Единичен reviewer срещу Council с еднакъв общ бюджет и вход | Отчет за предварително зададени дефекти, реални findings, false positives, пропуснат dissent, latency и наблюдавани разходи; без извод за превъзходство преди договорен праг |
| Q05 | При включване на UI/CLI представяне | Видими назначения, източници, partial/unknown/unsupported, отворени възражения и cleanup; views използват application use cases; визуалната проверка е по одобрения UI обхват |

Конкретните test packages и команди се задават в бъдещия implementation
plan. Live квалификацията изисква отделно разрешени harness заявки и не
следва автоматично от одобрението да се напише този spec. След code промени
се изпълняват приложимите Go проверки и регресии според task групата;
cross-build не се представя като native runtime доказателство.
