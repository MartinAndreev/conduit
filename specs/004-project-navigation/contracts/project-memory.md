# Проектен контекст, памет и външен адаптер

Дата: 2026-10-03. Статус: одобрена посока за автоматична фактическа история, преглеждана дълготрайна памет и заменяем backend. Подробните операции и lifecycle по-долу са предложение, не реализиран API. Engram е одобрен като опционална локална интеграция, включвана от потребителя; интеграцията още не е реализирана.

## Авторитетни данни и извличане

Conduit притежава одобрените spec документи, решенията, provenance и записаните outcomes. Външната memory система служи за индексиране, търсене и извличане; тя не става единственото място, от което зависят проектът и одобренията. Данните остават преносими. Одобрените документи и явно свързаните източници са достъпни и без външна семантична услуга.

Съществуващият локален Turso и документите са основа, но това не означава вече налични decision/memory repositories, export, outbox или schema. Те се проектират отделно. Memory адаптерът е различен от harness Provider и от raw DB connection.

## Категории

| Категория | Съдържание | Как става действаща |
| --- | --- | --- |
| Карта на проекта | Входни точки, компоненти, зависимости, полезни проверки | Проверено извличане/предложение с code evidence; преглед преди дълготрайна употреба |
| Архитектурно решение | Избор, причина, алтернативи, последствия | Човешко одобрение; има връзка към заменено решение |
| История на изпълнение | Какво е dispatch-нато, наблюдавано, проверено и прието | Автоматичен запис на установени събития; agent claim се обозначава като claim |
| Работно наблюдение | Откритие, хипотеза, потенциално полезен съвет | Предложение, докато не бъде прегледано; не се маскира като правило |

Автоматично създадено резюме на историята е производен текст с връзки към оригиналните събития. Моделен summary не е автоматично доказан факт. Reviewer може да провери предложена бележка, но не я превръща сам в одобрено архитектурно решение.

## Предложен запис

Идентичност, project scope, категория, кратко съдържание, източници и версии/хешове, произход/автор, време на наблюдение, последна проверена code revision, статус на прегледа, приложимост и връзка supersedes. Confidence score от backend не е approval. Статусът на одобрение и актуалността са отделни: исторически одобрено решение може да е заменено.

Промяна на свързаните файлове маркира нужда от проверка, не автоматично опровергаване. При непълни зависимости няма гаранция, че всички остарели записи ще бъдат открити. За ново решение не презаписваме безследно причината за старото. Изтриване, архивиране и замяна са различни действия; retention политиката предстои.

## Предложен lifecycle

Наблюдение → предложение с evidence → преглед → действащ запис. По-късно: нужда от проверка, заменен или архивиран. Човекът може да отхвърли предложение с причина. Агентите подават предложения за памет като част от отчета; не публикуват неявно глобални инструкции. Автоматичната фактическа история се води отделно от този approval flow.

## Заменяем адаптер — отговорности

- Inspect capabilities/health: какво действително поддържа backend и какво не е проверено.
- Index/update: производен запис с външен ключ към конкретна Conduit версия и project scope.
- Search/retrieve: query със задължителен project scope и филтри; резултати с source IDs, версии и retrieval metadata, не само свободен текст.
- Remove/reconcile: проследим резултат за премахване/обновяване на индекс; unknown не е success.
- Rebuild/export: Conduit трябва да може да възстанови производния индекс от собствените преносими източници. Native export capability може да е допълнение, не единствена гаранция.

Това са семантични операции, не имена на Go methods. При липса на backend филтър не разчитаме само на prompt „ползвай проект A“. Application проверява принадлежността, а deployment/storage границата трябва да предотвратява смесване на проекти. Backend namespace не е автоматично authorization boundary.

Conduit не приема backend резултат за действащ, ако локалната му версия вече е заменена/премахната. Предлагаме асинхронно индексиране след canonical commit със стабилни ключове и проследим sync статус. Няма разпределена транзакция с remote memory; при outage каноничният запис се запазва и индексът може да изостава. Конкретни outbox/retry/tombstone договори предстоят.

## Контекст за агента и ограничения

[Пакетът към агента](../../003-session-workflow/contracts/agent-assignment-context.md) включва само относимата памет плюс задължителните изрични документи. За всеки материал се вижда източникът и защо е включен. Паметта намалява повторното откриване на начални точки, но не отменя проверката на текущия код преди промяна.

При недостъпна memory услуга използваме достатъчния изрично свързан контекст с видимо ограничение; не скриваме липсващи задължителни входове. Не изпращаме credentials, сурови акаунт данни или несвързани project материали към индекс/модел. Remote backend, embeddings или extraction LLM имат отделен конфигурационен и бюджетен избор; интеграцията не разрешава автоматичен cloud fallback.

## Проектен UI

Предложение: „Контекст и решения“ с карта, решения, история, наблюдения и предложения за преглед. Детайлът показва provenance, статус, версия, replaced-by и последна проверка. При конфликт между спомен и актуален spec се показват и двата източника за разрешаване, без memory да получава приоритет по similarity score.

## Избор на продукт и PoC критерии

Оценяваме license, maintenance, local/offline deployment, Go интеграция, CPU/DB/LLM зависимости, project isolation, explicit metadata, update/delete/export, hybrid retrieval и разход. Hosted продукт и open-source core се разграничават. Започваме с явни връзки/търсене по документи; semantic backend не е задължителен за първия работещ flow.

PoC върху синтетични данни, само след отделно разрешение: еднакви термини в два проекта; заменено решение; променен source; duplicate index request; delete/reindex; memory outage; local-only inference/embeddings ако се изисква; export/rebuild; retrieval с доказуеми sources. Необходимите инсталации, модели и ресурси не са разрешени чрез настоящото проучване.

Отворени: стабилната версия на Engram и техническият механизъм за изтегляне, подробният lifecycle на локалния процес, schema и application ports, достъпите, context бюджетите, granular approval за карта/бележки, изтриване и правила при противоречие.

Документационно сравнение: [memory products research](../research/memory-products.md). Първоначалният shortlist е историческо проучване и е заменен за текущия обхват от изискването за локална памет и избора на опционален Engram.


## Engram като потребителска настройка

Одобрено: потребителят може да включи Engram за локална проектна памет. Не се изискват отделно поддържан сървър или Docker. Данните са в служебната директория на Conduit за съответния проект. Предложено представяне: „Настройки → Проект → Памет“, превключвател „Локална памет (Engram)“, изключен по подразбиране. Това е проектна настройка, не избор на harness или роля.

Предложено поведение за реализация:

- Изключено: Conduit не стартира Engram и не чете/пише неговия индекс. Основните spec документи, одобрения и фактическа история продължават да работят.
- Включване: проверява наличния executable и поддържаната версия, задава абсолютна project-specific директория (например `.conduit/memory/engram/`) чрез `ENGRAM_DATA_DIR` и управлява локален подпроцес през CLI/MCP stdio. Не използва споделената директория по подразбиране в home.
- Настройката и действителната готовност се показват отделно: изключено, проверка, готово, липсващ компонент, неподдържана версия или грешка. Запазено „включено“ не означава успешна подготовка.
- При липсващ компонент се показва необходимото действие. Одобрено: при включване Conduit изтегля необходимия Engram компонент и го стартира. Преди действието екранът обяснява това и защо се използва паметта; потребителят не трябва да инсталира отделна услуга ръчно.
- Изключването спира бъдещата употреба и освобождава управлявания процес безопасно; запазва данните. Изтриване е отделно явно действие. Вече доставеният контекст на активен агент не може да бъде отнет чрез превключвателя.
- При отказ на Engram явно свързаните документи остават достъпни. UI показва ограничението; не преминава към cloud или друг backend автоматично.
- Cloud sync, платен inference и изтегляне на embedding модели не се активират от тази настройка. Базовият режим е локална памет с текстово търсене.

Conduit остава собственик на прегледа и одобрението. Запис в Engram не превръща агентско наблюдение в одобрено решение. Когато Engram е изключен, това не изключва canonical проектната история.

Приемателни сценарии за бъдещата реализация: изключено не стартира процес; включване с налична/липсваща/неподдържана версия; отделни директории за два проекта; рестарт запазва настройката; отказът не блокира достъпа до spec; изключване не изтрива записи; повторно включване използва съществуващите данни; няма неразрешени мрежови операции. Проверява се конкретен stable release, а не само документацията на main.

Източници от проучването: [Engram](https://github.com/Gentleman-Programming/engram), [директория, CLI/MCP и операции](https://github.com/Gentleman-Programming/engram/blob/main/DOCS.md). Това е документационна основа, не изпълнен интеграционен тест.


### Изтегляне при включване — одобрено UX изискване

Екранът предварително обяснява: „Агентите намират предишни решения и полезен контекст, за да не проучват проекта отначало при всяка задача.“ Показва, че включването изтегля компонент от интернет и го стартира локално, а проектните данни остават в служебната папка. Не представя локалната памет като облачна синхронизация.

Поредност на видимите състояния: проверка на системата/наличния компонент → изтегляне при необходимост → проверка на файла → стартиране → проверка на готовността → готово. Процентът е от действително измерено изтегляне; при неизвестен размер има индикатор без измислен процент/ETA. Готовност се показва само след успешна проверка на компонента. При повторно включване подходящият наличен компонент може да се използва без ново изтегляне.

Предложени failure/cancel сценарии: липса на интернет, прекъснат download, недостатъчно място, невалиден файл, неподдържана платформа и неуспешно стартиране. Показват се засегнатата стъпка, разбираема причина и действие за повторен опит или отказ. Отказът не изтрива съществуваща памет и не оставя частичен download като готов executable. Точните checksum/signature, cache, atomic install, process cleanup и version/update правила предстоят преди реализация.

[Макет на подготовката](../screens/09-memory-setup.png): основният екран е по време на изтегляне. Долните две карета са илюстрации на следващи състояния, не едновременно работещи панели в реалния UI. Прогресът е примерен; няма извършен download или runtime проверка чрез генерирането на макета.
