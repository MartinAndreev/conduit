# 005 — Инициализация на Conduit

Дата: 2026-10-03. Статус: **одобрен от потребителя за етап A — application логика и тестове**. TUI/GUI изчакват приемането на A.

## Цел

При стартиране Conduit подготвя локалната си конфигурация, установява наличните Codex/OpenCode инструменти и връща разбираем резултат и проследим прогрес. Една application процедура обслужва TUI и GUI. Първо имплементираме и проверяваме тази обща логика; едва след приемането ѝ два Sol агента работят паралелно по интерфейсите.

## Приети изисквания

- Откриваме harness-ите преди създаване на началния конфиг.
- Съществуващите настройки се запазват. Липсващ, невалиден и нечетим файл са различни състояния.
- Прогресът показва действителни операции; непроверен достъп/модел не се представя като работещ.
- Няма автоматично inference, избор на платен модел или fallback.
- Бизнес логиката е отделна от двете приложения; интерфейсите показват state и подават команди.
- TUI посока: Bubble Tea v2, Bubbles, Lip Gloss; Glamour при Markdown.
- GUI посока: templUI/shadcn-templ 2.0 beta.10, фиксирана версия; desktop shell/templ bridge подлежат на отделна проверка.
- Engram е опционален и се изтегля при явно включване, с отделен прогрес. Startup не го включва автоматично.

## Предложен първи обхват

Подготовка без избран проект: разрешаване на application директории, прочит/валидация на конфиг, локално откриване на два harness-а, безопасно първоначално създаване, проверка на резултата, общо състояние за интерфейсите. Няма нужда от Turso база, за да създадем конфигурационен файл.

Не включва проектен каталог, импорт/създаване на проект, редактор на spec, роли и настройки като пълен CRUD, агенти/сесии, Engram installer, миграция от TypeScript, автоматични обновявания, detached service или синхронизация между работещи приложения. След startup първата UI реализация показва welcome; проектният home се включва с бъдещия каталог, а не се симулира като готова функционалност.

## Одобрени решения

| Решение | Предложение |
| --- | --- |
| Организация | Един Go модул; domain/application пакети, два composition roots за терминално и desktop приложение. Не отделен публикуван SDK на този етап. |
| Глобален конфиг | **Одобрено местоположение: `~/.conduit/config.yaml`**, чрез `os.UserHomeDir()` и platform-safe path join. Schema version 1 и YAML без тайни остават предложението за формат. Това е потребителски конфиг, не файл в текущия project cwd. |
| Проектни настройки | Бъдещ `.conduit/config.yaml`; този slice не го създава и не реализира merge/override политика. |
| Начални настройки | Два записа за поддържаните harness-и и наблюдаваните при създаване наличност/пътища; празни назначения на роли/модели; memory не се включва. |
| Повторно пускане | Ново откриване в паметта; конфигът остава byte-for-byte непроменен. Записаното старо наблюдение не е текуща наличност. |
| Липсващ harness | Startup може да завърши с предупреждение; welcome остава достъпен. Агентска работа още не е разрешена. |
| Невалиден конфиг | Блокиран startup с причина и път; никакво автоматично изтриване/поправка. Retry след външна корекция. |
| Метаданни | Само executable lookup и локален version probe; authentication и каталог модели са `unknown`. |
| Лимити | 3 секунди на version probe; 16 KiB общ capture на probe. Без автоматичен retry. |
| Конкурентен първи старт | Публикуване на цял файл само ако целта още липсва; загубилият процес прочита и валидира спечелилия файл. Няма overwrite. |

Потребителят одобри останалите решения след уточнението за `~/.conduit`. Последваща архитектурна промяна се съгласува преди имплементация.

## Потребителски flow

1. „Проверка на конфигурацията“ — намираме директориите и различаваме липса от грешка.
2. „Откриване на harness-и“ — Codex и OpenCode, независимо един от друг.
3. „Създаване на настройките“ — само при липсващ конфиг; иначе „Пропуснато: настройките вече съществуват“.
4. „Проверка на готовността“ — валидна конфигурация и честни наблюдения; не означава готов модел.
5. Успех → welcome; предупреждение → welcome с подробности; блокираща грешка → причината и Retry/Exit.

Отказът прекратява по-нататъшните стъпки и локалните probes. Ако файл вече е успешно публикуван, остава; Cancel не обещава rollback на завършени ефекти. Следващо стартиране може да го използва.

## Критерий за завършен application етап

Всички сценарии в [test-cases.md](test-cases.md) за общата логика са покрити, production adapters са проверени с временни директории и fake изпълними файлове, няма реални prompts, независимият одит е представен на потребителя. Работещ UI не е условие за този етап. Одобрението на application резултата е вход за двата UI агента.

## Допълнително одобрен Windows обхват — 2026-10-03

Потребителят изрично одобри ограничено разширение в съществуващия `internal/process` owner: Windows Job Object с kill-on-close, процесът се стартира suspended, присъединява се към job преди ResumeThread. Невъзможност за гарантирано ownership (включително nested-job ограничения) отказва launch и чисти suspended процеса/handles. Няма launch-to-assignment прозорец за escaping descendants. Startup detector използва общия process lifecycle; не заменяме Windows probes с отказ от откриване. Windows cross-compile не доказва runtime; реалният Windows тест остава отделна проверка.
