# Възлагане и контекст към агент

Дата: 2026-10-03. Статус: одобрена посока за трите слоя контекст; полетата и процедурите по-долу са проект на договор. Без Go имплементация или избор на storage schema.

## Три слоя

1. Проектен контекст: архитектура, приложими правила, карта на кода, команди за проверки и предишни решения.
2. Feature spec: човешкият договор за цел, обхват, архитектурни решения, интерфейси и приемателни сценарии. Spec Kit документите остават вход; наличието на tasks.md само по себе си не е достатъчно възлагане.
3. Конкретно възлагане: изпълнима задача с относимите части от първите два слоя, зависимости, ограничения и очакван отчет.

Архитектът определя смисъла и обхвата на задачата. Conduit проверява пълнотата, версиите и допустимостта, композира одобрените материали и доставя пакета. Оркестраторът не попълва липсващи архитектурни решения чрез предположения.

## Предложено съдържание на execution задачата

| Част | Изискван смисъл |
| --- | --- |
| Идентичност и основа | Project, feature/spec версия, plan/task identity, assignment/attempt и revision; разграничени от native session IDs |
| Цел и причина | Наблюдаем резултат и защо е нужен |
| Обхват и non-goals | Позволени промени, ограничения и изрично изключени действия |
| Входове и зависимости | Версионирани договори, приети решения и резултати от prerequisite задачи |
| Начални точки в кода | Проверени файлове/символи и съществуващи механизми; последна проверена code revision |
| Критерии | Какво трябва да е вярно при завършване; връзка с acceptance cases |
| Проверки | Конкретни разрешени операции, цел, environment, очакван evidence и ограничение на ефектите |
| Назначение | Роля, harness/model, приложими skills/instructions и snapshot на настройките |
| Workspace | Binding към изолирана работна среда и основание за разрешения обхват; owns не заменя enforcement |
| Лимити и ескалация | Разрешени ресурси/корекции; кога има нужда от архитект или човек |
| Отчет | Промени, проверки и фактически резултати, отклонения, blockers, рискове, предложения за памет |

Това е семантичен договор, не фиксиран JSON schema или списък Go полета. Съществуващият AssignmentRef в sessions вече има project/run/attempt/assignment/revision; новият пакет трябва да се свърже с него, без конкурираща се система от native идентичности. Feature/plan/task records още не са реализирани.

## Пакетът, който реално получава агентът

Предлагаме immutable context manifest за всяко dispatch възлагане: идентичност/версия, кодова основа, включени материали с source identity и версия/hash, приложими решения, зависими резултати и статус на memory retrieval. Reference сама по себе си не доказва, че материалът е доставен: manifest различава включен текст от достъпен за допълнително четене ресурс.

Задължителните правила, точната задача и разрешеният обхват се доставят независимо от класирането на memory search. Допълнителните записи се включват според относимост, актуалност и бюджет. Няма мълчаливо отрязване на задължителен договор при липса на място: нужен е по-малък обхват или явно уточнение. Summaries не заменят оригинала при спор и пазят източника си.

Фактите от паметта са контекст, не произволни инструкции. Memory backend не променя роли, разрешения, бюджети или одобрения. Ако ново извличане или редакция изменя активното възлагане, промяната е проследима; не подменяме стария manifest зад гърба на агента. Точният revision/Steer договор за допълнително доставен контекст предстои.

## Проверка преди dispatch — предложена процедура

1. Query на одобрения spec/план, task, настройки, dependencies и workspace факти.
2. Rule за допустимост/пълнота и актуалност; отказът е конкретен Kind/Reason, не просто false.
3. Събиране на изрично свързан контекст плюс относими memory кандидати; application правила проверяват scope/provenance/статус.
4. Запис на manifest и control intent; native dispatch извън DB транзакция; запис на outcome.

Memory outage не оправдава липсващ задължителен вход. Ако изрично свързаните материали са достатъчни, ограничението може да се покаже и flow-ът да продължи; иначе е нужен конкретен blocker. Това не обещава exactly-once външни ефекти.

## Пример за възлагане

Цел: свързване на Google акаунт към съществуващ профил според одобрения договор v4. Използвай посочения текущ механизъм за потвърждаване на собственост. Запази входа с парола. Работи в възложения файлов обхват. Провери успех, отказ и опит за свързване към чужд профил. Ако съществуващият механизъм не покрива договора, върни факти и архитектурен въпрос, вместо да променяш договора сам.

Файловете/командите се попълват от действително проучения проект; примерът не е готова task за изпълнение.

## UI и проверими сценарии

„Какво ще получи агентът“ показва задачата, източниците, решенията, manifest версията, липсите и memory ограниченията преди старт. Човекът може да коригира входа; не редактира вече изпратена immutable версия.

Бъдещи тестове: липсващ критерий; стара spec версия; неприключила dependency; memory от друг проект; mandatory context над budget; невалиден source; duplicate command; unknown dispatch; manifest възпроизвежда точните доставени материали; реалният отчет разграничава твърдения от доказателства.

Отворени решения: минимален schema, hashing/versioning, разпределение на context budget, precedence при конфликт, snapshot persistence и UI за корекции преди старт.
