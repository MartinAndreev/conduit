# Application договори — първи проект

Дата: 2026-10-03. Статус: **за обсъждане, без разрешение за имплементация**. Свързани документи: [flow](../spec.md), [проекти](../../004-project-navigation/spec.md).

Договор означава вход, обещан резултат, наблюдаеми ефекти и поведение при отказ или неизвестен изход. Не определяме още Go интерфейси, HTTP endpoints, CLI синтаксис или контроли на екраните. Старите контроли не са изискване за съвместимост; новите взаимодействия се проектират от потребителския сценарий.

## Установено и предложено

Установени са provider границата, revision точно +1 при Steer и разграничението между приета доставка и изпълнена корекция. Conduit проверява, човекът приема е потвърдено и като продуктова посока в [execution договора](execution-orchestration.md); точните production операции по-долу още се уточняват. Лесното превключване между проекти е потвърдена продуктова цел. Фоновото изпълнение при превключване още няма решение.

## 1. Работен речник и идентичност

| Понятие | Предложено значение |
| --- | --- |
| Project | Репозиторито/проектът, към който принадлежат работата и настройките. Избраният в UI проект не определя неявно адресата на вече изпратени действия. |
| Task | Човешкото намерение: цел, разрешен обхват и критерии за приемане. Запазва идентичността си при корекции. |
| Attempt | Конкретен опит за изпълнение на задачата; повторен опит е отделно действие, не скрит retry. |
| Assignment revision | Версия на конкретното възлагане към агента. Корекция в активното възлагане увеличава revision точно с 1. |
| Session / Turn | Каналът към harness и едно негово изпълнение. Не са равнозначни на цялата задача. |
| Candidate | Предложен резултат за точни attempt и revision; все още не е проверен или приет. |
| Verification | Доказателства от определени проверки върху конкретно състояние на workspace. |
| Acceptance | Човешко решение за точно този проверен резултат; не означава автоматично commit или merge. |

Task е предложение за продуктова единица, не нов пакет или таблица. В първия slice предлагаме един агент на задача. Последователните разработчик, проверки и независим reviewer са уточнени в [execution договора](execution-orchestration.md); паралелна работа още не е одобрена.

Предложение за адресиране: действие към съществуваща работа носи явни project/task/attempt идентичности и очаквана версия, според операцията. Application слоят проверява принадлежността им преди ефект. Native session/turn IDs се разрешават през записаното binding; UI не конструира native протокол.

Assignment revision и версията за конкурентна промяна на application състоянието са различни понятия. Финалният избор на ключове, обхват на идемпотентност и aggregate граници предстои.

## 2. Предложени операции

Работните имена по-долу описват намерението, не финален API.

| Операция | Вход | Обещан резултат / ефект | Важен отказ или неизвестност |
| --- | --- | --- | --- |
| PrepareTask | Project, цел, обхват, критерии, разрешени проверки, избор на harness/model и workspace | Записана чернова с липсващи изисквания; без стартиране на агент | Невалиден/недостъпен проект или непълен договор не се представя като готов за старт |
| StartTask | Подготвена задача, очаквана версия, command ID | Записано намерение и проследимо състояние на стартирането | Липса на capability/ownership отказва dispatch; неизвестната доставка не се повтаря автоматично |
| GetTask / ObserveTask | Явна идентичност; за историята — устойчив journal cursor | Snapshot и последователна активност, с обозначена непълнота при gap | Липса на telemetry не означава липса на работа или успех |
| CorrectTask | Точен attempt, очаквана assignment revision, текст на корекцията, command ID | Проследима доставка на предложение за revision +1 | Stale revision, липса на активен адресат или unknown delivery; receipt не доказва приложена корекция |
| VerifyCandidate | Candidate identity и договорени проверки | Report за точната revision и проверено workspace състояние | Непроследим/стар кандидат, липсваща проверка или променено съдържание не дава passed |
| AcceptCandidate | Candidate, verification reference, очаквана application версия и actor | Устойчиво записано човешко приемане | Конкурентна корекция или остаряла проверка изисква ясно решение; политиката предстои |
| RequestStop | Точен attempt и command ID | Записано намерение и отделен резултат за native спирането | Cancellation на чакането не доказва спряла работа; възможен е unknown |

Получаването на candidate от harness е вътрешен application flow, а не бутон за потребителя. Автоматичното задействане на проверки след candidate е отделно решение. Създаването на нов attempt след отказ/неуспех ще се договори изрично; CorrectTask тук означава корекция на активно изпълнение.

## 3. Общи гаранции — предложения за production

- Запис на намерението преди външен ефект; outcome след него. Не държим DB транзакция по време на harness RPC или проверка.
- Повторен command ID със същия вход чете наличния резултат/статус; различен вход със същия ID е конфликт. Локалната идемпотентност не обещава exactly-once доставка към harness.
- Application състоянието и съответното journal събитие се записват атомарно през ports. Съществуващият storage slice няма всички необходими records; схемата се проектира след договора.
- За всяко правило има конкретен typed Kind и човешки Reason. Техническата грешка остава отделна от очакван бизнес отказ; не въвеждаме универсален Decision за всички операции.
- Activity, доставка, резултат, verification, acceptance и cleanup имат отделни значения. Няма един общ boolean success, който ги слива.
- Смяната на видимия проект не пренасочва вече адресирана команда. Дали изпълнението продължава, спира или изисква действие при смяна е все още отворено.
- UI/CLI използват едни application операции; изгледите не управляват директно native sessions или raw DB connections.

## 4. Граници на първия договор

Codex вече предоставя проверим candidate канал. OpenCode live тестът доказа корекция и реален файл, но адаптерът няма ResultCandidate канал. Production flow за verification/acceptance през OpenCode изисква отделен договор; не превръщаме commentary, idle или успешно четене на файл в candidate без такова решение.

Няма договорени автоматичен retry, фонова услуга, resume след рестарт, Git promotion, topology на екип или конкретни UI контроли. Приемането на този речник не разрешава имплементацията им.

## 5. Ред за съгласуване

1. Основна продуктова единица: Task с цел и критерии, отделена от harness Session. Дали разговорът създава/уточнява задачата, или самият той е основната единица?
2. Project/workspace ownership и lifecycle, включително вече зададения въпрос за смяна на проекта при активен агент.
3. Точен договор за PrepareTask/StartTask и конкретен първи сценарий.
4. Наблюдение/корекция: конкурентни заявки, pending revision и неизвестна доставка.
5. Candidate/verification/acceptance: разрешени проверки, стабилно състояние на файловете, човешко решение и състезание с корекция.
6. Едва след това: окончателни DTOs, ports, persistence schema, тестови случаи и одобрена група за имплементация.

Това е отделен предшестващ flow: човекът може да пише и дискутира документа преди предаването към архитекта. Потвърдени са обсъждане без редакция, предложения чрез diff и общо достъпно ревю. Тази посока допълва работния речник по-горе; не утвърждава автоматично предложените execution DTOs или смесва document version с assignment revision.
